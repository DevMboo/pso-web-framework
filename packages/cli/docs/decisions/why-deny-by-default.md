## Context

Security that depends on remembering to add a check fails the one time someone forgets. Misconfiguration (a missing key, an empty issuer) is the most common way a "secured" service becomes open.

## Decision

Every default fails **closed**:

- A route needs `public: true` or a guard; neither is `PSO_ROUTE_007`.
- The `jwt` guard denies everything without issuer, audience and a key source, and accepts only asymmetric algorithms.
- Spring services allow only health checks and validate tokens themselves.
- Generators refuse to create public state-changing routes; Spring guards generated by `make:guard` deny by default (`allows()` returns `false`).
- The Compose file written by `pso docker:init` refuses to start without `PSO_JWT_ISSUER`, `PSO_JWT_AUDIENCE` and `PSO_JWT_JWKS_URI` (`${VAR:?...}`).
- The orchestrator refuses to **start** with a guarded route and incomplete JWT settings, and refuses symmetric algorithms and plain-http JWKS URLs: each refusal is reproduced in [Why the orchestrator refuses to start](/reference/startup-failures).

## Consequences

- A fresh project is secure but returns `401` everywhere until configured, which surprises newcomers; the troubleshooting page says so.
- Making something public is a visible, reviewable act.
- Tokens are validated twice (orchestrator and service): a small cost for defense in depth.

## Alternatives considered

Allow-by-default with security middleware to opt into (rejected) and trusting the orchestrator inside the network (rejected: bypassing the gateway would then bypass security).

## What it looks like in practice

The same guarded route, three callers (Expected output from a real run):

```text evidence="expected"
no token                                  -> 401 PSO_AUTH_UNAUTHORIZED
valid token without scope customers:read  -> 403 PSO_AUTH_FORBIDDEN
valid token with the scope                -> forwarded to the service
```

and a fresh orchestrator with a guarded route but no JWT settings is flagged before it ever runs:

```text evidence="expected"
HIGH     SEC005 gateway
         jwt guard is used but security.authentication.issuer, security.authentication.audience, a key source (security.authentication.jwks.uri or security.authentication.publicKey.file) is not configured ...
FAILED
```

## The cost, and how to live with it

The first request to a new route fails until it has a token. Three habits help: keep a local development key and a token helper ([running the environment](/getting-started/running)); read the `WARN [security]` line, which states the reason (`missing_header`, `missing=scope:...`); never "fix" a `401` by disabling verification.

## When to revisit

Never toward allow-by-default. Revisit only the *ergonomics*: shorter paths to a working development token. The defaults stay.
