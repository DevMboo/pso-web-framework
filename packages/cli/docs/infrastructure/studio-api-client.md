`pso studio` adds these areas in 0.2.0; each one reads the same engine as the CLI, so Studio and the `infra:` commands cannot disagree.

| Area | Shows | Operations (`pso studio --ops`) |
|---|---|---|
| Infrastructure | environment, resources by module with owner, status and next action, validation and live probes | apply, repair |
| Containers | topology in dependency order, state and health, logs (redacted) | start all / one, restart one, stop one, stop all (volumes are kept) |
| Hosts | public hosts, addresses as containers and as processes, the hosts block | - |
| Certificates | authorities and certificates (names, expiry, fingerprint), secrets (source and length only) | rotate (development) |
| Deployment | the deployment plan, blockers, prerequisites, frontend publication, releases | - (deployments run from the CLI) |
| Frontend | every shell with its own microfrontends, public mounts | (as before, `--frontend-ops`) |
| API Client | endpoints, request builder, responses, saved requests, history | sends requests |

Without `--ops` these pages are read-only. With it, every operation needs a typed confirmation (`restart fei-admin`, `apply local`) that the server checks again, plus the same CSRF defence as every mutating Studio endpoint (same-origin `Origin`, a custom header, JSON only). A non-development environment must additionally be acknowledged by name. Deleting data volumes is a CLI-only action.

## API Client

Endpoints are discovered from the orchestrator's `ROUTES.pso.ts` (method, path, access) and the services' operation contracts. A request is built from a **target**, a method, a path, path parameters, query parameters, headers, a body (JSON, raw with a content type, form fields, or form-data with file uploads), authentication, variables and a timeout. Every method is available: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.

Authentication:

- **Development user**: the server obtains a real token for a declared development user from the environment's Keycloak (password grant through the development-only client) or signs one with the pso-dev identity. The token never reaches the page.
- **Bearer**: a token you paste.

The response shows status, time, size, whether TLS was verified, headers and the body (JSON formatted). Requests can be cancelled; the timeout is enforced by the server.

### The execution boundary

The API Client runs requests on the Studio server so it can verify TLS against the environment's authority and resolve local host names. It is **not a proxy**:

- a request names a target (`edge:api`, `edge:<fei>`, `service:<name>` when services are published, `process:<name>`), never a URL; the server builds the URL and refuses it if the origin changed;
- paths with a scheme, a host, `//` or dot segments, forged `Host`/`Content-Length`/`Transfer-Encoding` headers, header injection and bodies on GET/HEAD are refused;
- redirects are returned, never followed; request bodies are limited to 10 MB, responses to 5 MB;
- a service that requires mutual TLS is not offered as a direct target (call it through the orchestrator);
- requests to a staging or production environment need `pso studio --ops`.

### History and collections

The last 100 requests are kept in `.pso/studio/api-history.json`, readable by its owner only: method, path, masked query values and headers (`Authorization: Bearer [REDACTED]`, cookies, API keys, anything named like a token or secret), status and time; **no bodies**. Saved requests (`.pso/studio/api-collections.json`) store sensitive header values as `{{name}}` references, and variables whose name looks sensitive are kept in memory only. Response bodies are shown as received, except values PSO knows are secret (environment secrets, issued tokens, tokens typed into the client), which are masked.

### Reference requests

A CRUD module generated by `pso create orchestrator` or `pso make:crud` ships a version-controlled collection,
`<orchestrator>/docs/api/<resource>.collection.json`. Studio lists it under **Reference requests**: options (public), create, list with
page, size and sort, filter, find, update, delete, and the expected failures (invalid body `400`, duplicate `409`, missing `404`,
unauthorized `401`, forbidden `403`). Loading one fills the builder; it is sent with a development user, never with a stored token: the
file holds **no credential**, only `"auth": { "kind": "dev-user" }`, and is safe to commit.

Requests target the orchestrator (`edge:api`), which is how clients use the API. The collection also carries one request **directly to
the microservice** (for example `process:catalog`, labelled "bypasses the orchestrator"): it is for diagnosing the service, which then
authorizes the token itself.

## Limits
- Direct requests to services need `publishServices: true` in Docker mode, or the services running as local processes.
- A service that requires mutual TLS is reached through the orchestrator only.
- WebSocket channels are not exercised by the API Client.
