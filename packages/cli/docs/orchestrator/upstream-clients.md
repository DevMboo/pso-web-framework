```typescript
@Get("/")
async findAll(@Req() req: IncomingMessage, @Res() res: ServerResponse) {
  return this.upstream.forward(req, res, "catalog");
}
```

with `metadata: { service: "catalog" }` on the route. `forward` refuses a service that differs from the route's declared one, so the route registry stays the single source of truth.

## Where services come from

| Environment | Source |
|---|---|
| Development | `pso.workspace.json` (the services' `port`, on `127.0.0.1`) |
| Production | `PSO_UPSTREAM_<NAME>=host:port`, e.g. `PSO_UPSTREAM_CATALOG=catalog:8081` (what the generated Compose file sets) |

Nothing scans ports. A malformed `host:port` stops start-up. **Discovery never implies authorization**: the route's guard decides who may call.

## Request hygiene

- Client `x-pso-*`, `x-forwarded-for` and `x-correlation-id` headers are dropped; a fresh correlation id is sent.
- `Authorization` is forwarded only on guarded routes, so the service validates the token itself.
- Hop-by-hop headers are removed; the upstream timeout (`UPSTREAM_TIMEOUT_MS`, default 5 s) and body limit apply.
- If an action consumed the body with `@Body()`, the raw body is re-sent. Actions generated by `make:route --upstream` and `make:resource` do not consume it.

## Failure modes

| Situation | Response |
|---|---|
| Upstream refused the connection or cannot be resolved | `503 upstream_unavailable` |
| Upstream timed out (connect, idle or total deadline) | `504 upstream_timeout` |
| Upstream reset the connection or sent an invalid response | `502 bad_gateway` |
| Upstream response larger than `MAX_UPSTREAM_RESPONSE_BYTES` (declared length) | `502 upstream_response_too_large` |
| Request body larger than `MAX_BODY_BYTES` | `413 payload_too_large` |
| Service name not registered | `502 unknown_service` |
| Route and action disagree on the service | `500` (a programming error) |

There are no automatic retries or circuit breakers in this version.

## Limits

Limits are read from environment variables at start-up and validated; an invalid value stops the process and names the variable. Streaming is enforced while bytes flow, so memory stays bounded.

| Variable | Default | Meaning |
|---|---|---|
| `MAX_BODY_BYTES` | 1048576 | request body; checked from `Content-Length` and while streaming |
| `MAX_UPSTREAM_RESPONSE_BYTES` | 10485760 | upstream response body |
| `MAX_HEADER_BYTES` | 16384 | request line plus headers (`431` when exceeded) |
| `UPSTREAM_TIMEOUT_MS` | 5000 | connect and idle time of an upstream socket |
| `UPSTREAM_RESPONSE_TIMEOUT_MS` | 30000 | deadline for the whole upstream exchange |
| `HEADERS_TIMEOUT_MS` / `REQUEST_TIMEOUT_MS` / `KEEP_ALIVE_TIMEOUT_MS` | 10000 / 30000 / 5000 | client-side timeouts |
| `MAX_CONNECTIONS` | 1000 | open connections |
| `MAX_CONCURRENT_REQUESTS` | 0 (unlimited) | above this, requests get `503 server_busy` with `Retry-After` |
| `MAX_UPLOAD_BYTES` | 10485760 | a whole `multipart/form-data` request, counted while it streams (a DTO's own file limits apply inside it) |
| `MAX_MULTIPART_PARTS` | 50 | parts (fields and files) of one multipart request |
| `MAX_CONCURRENT_UPLOADS` | 16 (0 = unlimited) | uploads being received at once; above this `503 server_busy` with `Retry-After` |

When an upstream response exceeds the limit **after** headers were sent (chunked streams), a second status is impossible: the stream is closed abnormally, the upstream transfer is terminated and a warning is logged. A client that disconnects cancels the upstream request. With `NODE_ENV=production` a critical limit set to more than 100 times its default is refused.

Each limit is also a configuration key (`http.limits.maxBodyBytes`, `http.limits.maxUpstreamResponseBytes`, `http.limits.upstreamTimeoutMs`, ...) that can be set in `pso.config.json`, per environment in `pso.config.<environment>.json`, or with `PSO_CFG_http__limits__<name>`; the variable in the table always wins. See [Rate limiting](/security/rate-limiting) for the precedence rules and `http.rateLimit.*`.

TLS, mutual TLS, credential-forwarding policy per upstream and certificate rotation are described in [Service identity and mutual TLS](/security/service-identity).

## Uploads and downloads

`forward()` relays the request exactly as it arrived. Files get two dedicated methods, both on the same `Upstream` provider, both bound to the route's declared `metadata.service`:

| Method | Use | What it guarantees |
|---|---|---|
| `forwardUpload(req, res, service, dto, { path })` | the DTO was bound with `@Body(Dto)` and has `@FileField` fields | a **new** multipart request is built from the validated fields and files (nothing of the client's body, `Content-Type`, boundary or identity headers is relayed), streamed from the temporary files with an exact `Content-Length`; correlation, trace and the credentials your upstream policy allows travel as in `forward()` |
| `forwardDownload(req, res, service, { path, maxResponseBytes })` | stream a stored file to the client | backpressure both ways, abort on client disconnect, a per-route size cap (default `MAX_UPSTREAM_RESPONSE_BYTES`), and on `2xx` responses `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cache-Control: private, no-store` and `Content-Disposition: attachment` unless the service chose one |

See [File uploads and downloads](/orchestrator/file-uploads) for a complete example.

## What the caller sees

When the upstream behaves, the gateway is transparent. When it does not, the answer is a standard problem with a stable code (verified for the unavailable case):

| Upstream condition | Answer |
|---|---|
| answers | the upstream's status and body |
| connection refused (service down) | `503 PSO_UPSTREAM_UNAVAILABLE` |
| does not answer in time | `504 PSO_UPSTREAM_TIMEOUT` |
| unknown service name | `502 PSO_UPSTREAM_UNKNOWN_SERVICE` |
| invalid or oversized answer | `502` (`PSO_UPSTREAM_BAD_GATEWAY`, `PSO_UPSTREAM_RESPONSE_TOO_LARGE`) |
| TLS verification failed | `502 PSO_UPSTREAM_TLS` |

Verified body for the unavailable case:

```text evidence="verified"
HTTP 503 application/problem+json
{"type":"urn:pso:problem:upstream-unavailable","title":"Upstream unavailable","status":503,"detail":"An upstream service could not be reached.","code":"PSO_UPSTREAM_UNAVAILABLE","error":"upstream_unavailable","instance":"/customers","correlationId":"doc-corr-0004"}
```

## Troubleshooting a forward

1. `pso services:health`: is the service up? (verified output: `DOWN catalog http://127.0.0.1:8081/actuator/health`).
2. `pso routes:inspect <route>`: does the route point at the service and port you expect?
3. In production, is `PSO_UPSTREAM_<NAME>=host:port` set (the service name in upper case, hyphens as underscores)?
4. Read the service's own log with the same correlation id: the orchestrator forwards `x-correlation-id`.
5. For timeouts, compare `http.limits.upstreamTimeoutMs` with the service's real latency before raising it.

## Variations

| You want | Do |
|---|---|
| a longer timeout for slow endpoints | raise `http.limits.upstreamTimeoutMs` for the gateway; fix the slow endpoint first |
| to forward the user's token | the default for guarded routes under the upstream's policy; bind it with `audience` ([service identity](/security/service-identity)) |
| to never forward the token | `forward: "none"` for that upstream |
| TLS or mutual TLS to the service | per-upstream settings ([service identity](/security/service-identity)) |

## Composing a response from several services: `UpstreamClient`

`Upstream.forward` hands the current request to **one** service. An action that needs data from several services (a customer summary built from the customers, orders and catalog services) uses `UpstreamClient` instead: it calls registered services by name and the action builds the response. The orchestrator coordinates; the business rules stay in the services.

```bash
pso make:route summary show --method GET --path /of/:id --compose customers,orders,catalog --scopes summary:read --service gateway
```

The generator injects the client and, in `ROUTES.pso.ts`, declares the services the action may call:

```ts title="src/modules/summary/routes/ROUTES.pso.ts (the generated entry)"
{
  method: "GET",
  path: "/summary/of/:id",
  controller: SummaryController,
  action: "show",
  security: { guard: "jwt", scopes: ["summary:read"] },
  metadata: { services: ["customers", "orders", "catalog"] }
}
```

```ts title="src/modules/summary/controllers/summary.controller.ts"
import { Controller, RestController, Get, Param, UpstreamClient } from "@pso/http";

interface Customer { id: string; name: string }
interface Order { id: string; productIds: string[] }
interface Product { id: string; title: string }

@Controller()
@RestController("/summary")
export class SummaryController {
  constructor(private readonly services: UpstreamClient) {}

  @Get("/of/:id")
  async show(@Param("id") id: string) {
    const customer = await this.services.get<Customer>("customers", "/customers/:id", { params: { id }, credentials: "caller" });
    const orders = await this.services.get<Order[]>("orders", "/orders", { query: { customerId: id } });
    const ids = [...new Set(orders.flatMap((o) => o.productIds))];
    const products = await Promise.all(ids.map((pid) => this.services.get<Product>("catalog", "/products/:id", { params: { id: pid } })));
    return { customer, orders, products };
  }
}
```

| Rule | Detail |
|---|---|
| Destination | the **name** of a registered service; there is no URL parameter. The path is relative to the service, and its endpoint prefix is applied once, by the client |
| Declaration | inside a request the service must be listed in the route's `metadata.services` (or be its `metadata.service`). A call to any other service is refused before anything is sent (`PSO_UPSTREAM_POLICY`, and the log names the missing declaration). `pso validate` refuses a name that is not a service of the workspace (`PSO_ROUTE_010`) |
| Path and query | `:name` segments are replaced from `params`, each encoded as one segment; `..`, `//`, `?`, `#` and encoded separators are refused; the query goes in `query` |
| Transport | the upstream's own TLS and mutual TLS configuration (the one `forward` uses); verification is never disabled; in production plain HTTP to another host is refused at start-up as for `forward` |
| Credentials | none by default. `credentials: "caller"` sends the bearer token of the current request, and only when the upstream policy, the transport and the token audience allow it; a refusal is an error, not a silent omission |
| Correlation | the correlation id and the trace of the current request travel with every call |
| Deadline | `timeoutMs` per call, at most (and by default) `http.limits.upstreamResponseTimeoutMs` |
| Cancellation | `signal` (an `AbortSignal`); and when the client of the current request disconnects, the calls made for it are aborted |
| Response | JSON (or `responseType: "text"`), read up to `maxResponseBytes` (default `http.limits.maxUpstreamResponseBytes`); redirects are never followed |
| Methods | `get`, `post`, `put`, `patch`, `delete` return the parsed body; `call` returns `{ status, headers, data }` |

### Failures

Every failure is an `UpstreamCallError` with `service`, `kind` and, for an answer of the service, `status` and the parsed `problem`. Left unhandled it becomes a stable problem that never contains the service's response body:

| `kind` | What happened | Problem when unhandled |
|---|---|---|
| `status` (404) | the service answered 404 | `404 PSO_UPSTREAM_NOT_FOUND` |
| `status` (409) | the service answered 409 | `409 PSO_UPSTREAM_CONFLICT` |
| `status` (other 4xx, 3xx) | the service refused the request | `502 PSO_UPSTREAM_REJECTED` |
| `status` (5xx), `invalid_response` | the service failed or answered something else than JSON | `502 PSO_UPSTREAM_BAD_GATEWAY` |
| `timeout` | no answer within the deadline | `504 PSO_UPSTREAM_TIMEOUT` |
| `unavailable` | the service could not be reached | `503 PSO_UPSTREAM_UNAVAILABLE` |
| `tls` | the certificate or the handshake was rejected | `502 PSO_UPSTREAM_TLS` |
| `response_too_large` | the answer exceeds the limit | `502 PSO_UPSTREAM_RESPONSE_TOO_LARGE` |
| `policy`, `unknown_service` | refused before anything was sent | `500 PSO_UPSTREAM_POLICY`, `502 PSO_UPSTREAM_UNKNOWN_SERVICE` |

An action that knows what a downstream answer means translates it on purpose:

```ts
import { HttpError, UpstreamCallError } from "@pso/http";

try {
  return await this.services.get("customers", "/customers/:id", { params: { id } });
} catch (e) {
  if (e instanceof UpstreamCallError && e.is(404)) throw new HttpError(422, "unknown_customer");
  throw e;
}
```

Limits: one attempt per call (no retries, no circuit breaker), no distributed transaction and no saga: if the second call fails after the first one changed data, undoing it is the application's design decision.

## The service prefix outside the workspace: `PSO_UPSTREAM_<NAME>_PREFIX`

With the workspace file the orchestrator knows each service's endpoint prefix. In a container there is no workspace file: the address comes from `PSO_UPSTREAM_<NAME>` and the prefix from `PSO_UPSTREAM_<NAME>_PREFIX`. Both `forward` and `UpstreamClient` put that prefix in front of the path.

```yaml title="what pso docker:init writes for the orchestrator"
PSO_UPSTREAM_CATALOG: "catalog:8081"
PSO_UPSTREAM_CATALOG_PREFIX: "/catalog"
```

In a deployment you write by hand, set both for every service that has a prefix. Without the prefix variable every forwarded path misses it and the service answers 404 for routes that work in development.

## Service and guard names checked by the compiler

```bash
pso types
```

writes `src/pso-types.d.ts` from `pso.workspace.json` and the guards of the project. From then on `metadata.service`, `metadata.services`, `security.guard`, `Upstream.forward` and `UpstreamClient` accept only names that exist, in the editor and in `npm run typecheck`. It is optional: without the file every string is accepted, as before, and `pso validate` and start-up keep checking either way. Run it again after adding a service or a guard (`pso types --check` in a pipeline).

## Common mistakes

- Raising the timeout instead of fixing the slow service.
- Forgetting that a route's `metadata.service` must equal the service the action forwards to (otherwise a `500` programming error).
- Declaring a service in the workspace but not setting `PSO_UPSTREAM_*` in production.
