> [!STATUS]
> **Implemented and verified.** Generated by the distributed CLI into a new workspace, built, started with real PostgreSQL and the identity provider in Docker, and called through the orchestrator and directly: every status below was observed, the data survived a restart, and the generated tests pass.

`pso create service catalog` generates a working Product API in the layered Java structure; `pso create orchestrator gateway` generates
the matching `products` module and binds it to the service that serves `/products`. Both are **examples to keep or remove**: nothing
in the framework depends on them, and `--template empty` creates the same projects without them.

## The resource

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | assigned by the service |
| `sku` | string | required, 3-64 characters, upper-case letters, digits and inner hyphens (`KB-100`), **unique** (database constraint) |
| `name` | string | required, 1-120 characters |
| `description` | string | optional, at most 2000 characters |
| `price` | decimal | required, `>= 0`, at most 10 integer digits and 2 decimals (`NUMERIC(12,2)`, `BigDecimal`; sent as a string) |
| `active` | boolean | defaults to `true` |
| `createdAt`, `updatedAt` | timestamp | UTC (`TIMESTAMPTZ`), set by the service |

## Endpoints

| Method and path (orchestrator) | Scope | Answers |
|---|---|---|
| `GET /products/options` | public | 200: the sortable and filterable fields and the page limits (no data, no backend call) |
| `POST /products` | `products:write` | 201 + `Location`, 400, 401, 403, 409 (duplicate SKU) |
| `GET /products?page&size&sort&sku&name&active` | `products:read` | 200 (a page), 400 (bad page, size or sort field) |
| `GET /products/{id}` | `products:read` | 200, 400 (not a UUID), 404 |
| `PUT /products/{id}` | `products:write` | 200, 400, 404, 409 |
| `DELETE /products/{id}` | `products:write` | 204, 404 |

The microservice serves the same API under its prefix (`/catalog/products`), checks the token and the scopes **again**, and is reachable
only inside the workspace network: the browser and other clients use the orchestrator. Every error is an RFC 9457 problem
(`application/problem+json`) with the same shape on both sides; a duplicate SKU is `409 conflict` with the detail "a product with this
sku already exists" (the submitted value is not echoed).

## How a request flows

1. The orchestrator matches the route in `routes/ROUTES.pso.ts`; the `jwt` guard validates the token and the scope (401 / 403 here).
2. The controller validates parameters and the body with the DTO decorators (400 before anything is called) and delegates to the service.
3. `ProductProvider` calls the service **by name** (`UpstreamClient`, the binding constant `PRODUCT_SERVICE`) with the caller's token
   (`credentials: "caller"`) and the correlation id; it translates the service's 404 / 409 / 400 into the same problems.
4. In the microservice the PSO security starter validates the token again, `@PreAuthorize` checks the scope, `@Valid` validates the
   record, and `ProductService` runs the operation in a transaction.
5. PostgreSQL enforces the constraints (the unique SKU among them); pagination, sorting and filters run in the query.
6. The mapper returns the public response; the entity never leaves the service.

## The files

### Microservice (`catalog`)

| File | What it does |
|---|---|
| `application/rest/ProductController.java` | HTTP: `@Valid` bodies, `@PreAuthorize` scopes, 201 + `Location`, 204 |
| `application/service/ProductService.java` | the operations, each `@Transactional`; the SKU check plus the constraint violation turned into 409 |
| `application/dto/request/CreateProductRequest.java`, `UpdateProductRequest.java` | records with Jakarta Validation |
| `application/dto/response/ProductResponse.java`, `PageResponse.java` | the response record and the stable page contract |
| `application/mapper/ProductMapper.java` | request -> entity -> response |
| `infrastructure/entity/ProductEntity.java` | the JPA entity (`@Version`, UTC timestamps) |
| `infrastructure/persistence/ProductRepository.java`, `ProductSpecifications.java` | Spring Data + database-level filters |
| `shared/exception/*.java` | `ResourceNotFoundException`, `ConflictException`, `InvalidRequestException` (RFC 9457 problems) |
| `shared/validation/PageRequests.java` | page, size (maximum 100) and the allowed sort fields |
| `src/main/resources/db/migration/V1__create_products.sql` | the table, its constraints and indexes (Flyway; Hibernate only validates) |
| `src/test/java/.../application/rest/ProductControllerTests.java` | the API tests: real context, real JWTs, embedded PostgreSQL |
| `docs/reference-crud.md` | this list for the project, with the removal steps |

```sql
-- src/main/resources/db/migration/V1__create_products.sql (generated, excerpt)
CREATE TABLE products (
    id           UUID             PRIMARY KEY,
    sku          VARCHAR(64)      NOT NULL CHECK (char_length(sku) >= 3),
    price        NUMERIC(12, 2)   NOT NULL CHECK (price >= 0.00 AND price <= 9999999999.99),
    created_at   TIMESTAMPTZ      NOT NULL,
    CONSTRAINT uk_products_sku UNIQUE (sku)
);
```

## Binding the module to its service

The orchestrator finds the service that serves `/products` in `pso.workspace.json`; no service name is assumed. Created **before** the
service, the module still compiles and starts, `pso validate` warns `PSO_CRUD_UNBOUND`, and its routes answer `502` (`unknown_service`) while the start-up
log names the missing service and the fix; `pso create service` binds it as soon as the service exists. To bind it yourself:

```bash
pso crud:bind products --to catalog
```

## Running it

```bash
pso infra:init --identity keycloak --runtime docker --users "ana,bob:products:read"   # declare Docker, Keycloak, development users
pso docker:up --vendor        # PostgreSQL, Keycloak, the service, the orchestrator and the edge, provisioned by PSO
pso studio                    # API client: the "Reference requests" panel holds the collection, sent with the dev user
```

Locally without the containers of the projects: `./mvnw spring-boot:run` in `catalog` against a PostgreSQL database (`DB_URL`,
`DB_USER`, `DB_PASSWORD`; the `h2` profile does not apply to this service) and `npm run dev` in `gateway`. `./mvnw test` and `npm test` run the generated tests. The database password and the development user
are generated per workspace into `.infra/` and never written into source or into the collection.

In Studio the collection's requests go to the **orchestrator** (`edge:api`): that is how clients use the API. A request sent directly
to the microservice is labelled as such and needs a token of its own: it is for diagnosing the service, not for clients.

## Removing it

Delete the files listed above (the project's `docs/reference-crud.md` lists them for the project) and, if the table holds nothing you
need, add a migration that drops it (`pso make:migration drop-products`) instead of editing `V1`. Remove the `products` module
directory from the orchestrator. `pso validate` confirms the result.

## Another resource the same way

```bash
pso make:crud order --service catalog --orchestrator --fields "code:string:unique:length=3-32:filter:sort,total:decimal:precision=12:scale=2:min=0:sort"
```

generates the same set of files for `order` (the next migration number, its own scopes `orders:read` / `orders:write`, tests and a
collection): see [Generators](/architecture/generators).

## What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| every request `502 unknown_service` | the module is bound to a service the workspace does not have | `pso create service <name>` or `pso crud:bind products --to <service>` |
| `401` from the orchestrator | no token, or one from another issuer | send it with the development user from Studio, or a token of the workspace's identity provider |
| `403` | the token lacks `products:read` / `products:write` | grant the scope to the user in the identity provider |
| `409 conflict` on create | the SKU exists (also when two requests race: the database constraint decides) | use another SKU |
| `400` on list | a sort field the endpoint does not allow, or `size` above 100 | `GET /products/options` lists what is allowed |
