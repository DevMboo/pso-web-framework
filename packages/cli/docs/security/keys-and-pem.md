PSO uses Node's vetted crypto (no custom algorithms) to create keys for development and testing, and it reads PEM keys and certificates for verification.

> [!WARNING]
> Keys generated by `pso security:keys` are for development and testing. In production, let your identity provider hold the private key and publish a JWKS. `pso security:check` fails the build (`SEC001`, critical) if private key material sits in a file that is not git-ignored.

## Generate and list

```bash
pso security:keys --generate --alg ES256      # or --alg RS256 (3072-bit)
pso security:keys                             # list keys: public data only
```

Verified output:

```text evidence="verified"
$ pso security:keys --generate --alg ES256
generated k-20261108-21b1a884 (ES256); private key: keys\k-20261108-21b1a884.private.pem (owner-only ACL applied); public JWKS: keys\jwks.json
active    k-20261108-21b1a884  ES256  2026-11-08T14:56:58.368Z
```

| Created | Where | Protection |
|---|---|---|
| `<kid>.private.pem` | `keys/` | git-ignored (`keys/*.private.pem` is appended to `.gitignore`), mode `0600`, or an owner-only ACL on Windows; **never printed** |
| `<kid>.public.pem` | `keys/` | public |
| `jwks.json` | `keys/` | public keys only, ready to serve as a JWKS |
| `index.json` | `keys/` | key ids, algorithms, status |

## Rotation: step by step

Rotation replaces the signing key without invalidating tokens that are still alive:

```bash
pso security:rotate --dry-run    # shows the plan, changes nothing
pso security:rotate              # new active key; the previous one becomes "retiring" and stays in the JWKS
# ... wait until tokens signed with the old key have expired ...
pso security:rotate --retire <kid>
```

Verified output of a rotation:

```text evidence="verified"
$ pso security:rotate --dry-run
[dry-run] would create a new ES256 key and demote k-20261108-21b1a884 to retiring

$ pso security:rotate
new active key k-20261108-b7b7441b (owner-only ACL applied)
retiring (still in JWKS): k-20261108-21b1a884
after tokens signed with old keys have expired: pso security:rotate --retire <kid>

$ pso security:keys
retiring  k-20261108-21b1a884  ES256  2026-11-08T14:56:58.368Z
active    k-20261108-b7b7441b  ES256  2026-11-08T15:18:27.378Z
```

During the overlap, tokens signed with the old key still validate because both public keys are in `jwks.json`. A key id that does not exist is refused (`error: Unknown key "nonexistent"`), and the active key cannot be retired.

How long to wait: at least the longest lifetime of a token you issued (its `exp`) plus the verifier's clock tolerance and JWKS cache TTL (`security.authentication.jwks.cacheTtlSeconds`, default 600 s). Retiring earlier makes still-valid tokens fail with `401`.

## Using PEM in the guard

Point `PSO_JWT_PUBLIC_KEY_FILE` at a PEM public key or X.509 certificate and set one algorithm ([Authentication](/security/authentication)). In development that is a file path such as `../keys/<kid>.public.pem`. This applies to **orchestrators only**: a Spring service refuses to start without `PSO_JWT_JWKS_URI` (https, or http on loopback), so give Spring the generated `keys/jwks.json` through a loopback URL ([worked example](/architecture/manual-crud-0-1#12-give-both-services-a-way-to-verify-tokens)).

## Variations

| Situation | Approach |
|---|---|
| development | generated keys and a PEM file; mint your own test tokens with the private key |
| production with an identity provider | `PSO_JWT_JWKS_URI` (https), no private key anywhere in your repository |
| you operate your own issuer | publish `jwks.json` over https, rotate on a schedule, keep the private key in a secret manager |
| a certificate instead of a bare key | the guard accepts X.509 and checks its validity period |

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `SEC001` critical | the private key is not ignored: add `keys/*.private.pem` to `.gitignore`, remove it from history, rotate |
| all tokens fail after rotation | the verifier cached the old JWKS or the old key was retired too early: wait for the cache TTL, check `jwks.json` |
| `401` with a valid-looking token in development | the PEM file path in `PSO_JWT_PUBLIC_KEY_FILE` is relative to the wrong directory |

## Permissions of development keys

Private keys the CLI writes are readable by their owner only where the file system has modes: the signing keys of `pso security:keys`, the development issuer's key (`idp/keys/`), the development authority's key (`tls/ca.key`) and each service's `tls/<service>/tls.key` are mode `0600`. They are never copied into an image or a distribution artifact (`.dockerignore` excludes keys and PEM files, and `pso dist` refuses them).

| Platform | What applies |
|---|---|
| Linux | a container reads a mounted key only when it runs as the user that owns the file. The generated `docker-compose.yml` runs every container as `PSO_CONTAINER_USER`; `pso docker:init` sets its default to the user who ran it, and on another machine you set `PSO_CONTAINER_USER=$(id -u):$(id -g)` in `.env`. A container that cannot read its key fails at start-up with a TLS error that names the file |
| Windows, macOS (Docker Desktop) | file modes are not carried into the container; the access control of the directory is what protects the files. Leave `PSO_CONTAINER_USER` unset |
| Production | keys come from your certificate authority or secret store with the ownership you choose; PSO does not generate, ship or reuse production keys |

Limit: the Linux user mapping was verified against the principle (a `0600` file is readable only by its owner inside a container) and by generating the files, not by running the full generated deployment on a Linux host.
