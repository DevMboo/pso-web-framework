# pso-cloud-validation (fixture)

**Responsibility: cloud deployment, infrastructure, operational security and remote management.** It answers "does PSO deploy, operate,
observe and recover a real distributed application on a real Linux server?" Functional correctness of the Commerce domain is the job of
[`../pso-commerce`](../pso-commerce/README.md), not of this fixture.

## Why this is not the Commerce fixture

Both use the same business domain (customers, catalog, orders, a gateway), but they are separate implementations: different data models
and migrations, different events (this one adds an outbox, stock reservations and `OrderEvents`/`InventoryEvents`), different API
contracts and different ports. Do not copy functional changes between the two: change the fixture whose responsibility the test belongs
to. The only byte-identical file, `infra/dispatch/rabbitmq.compose.yml`, is generated by `pso dispatch:install rabbitmq` in each workspace.

## Layout

| Path | What it is |
|---|---|
| `gateway/` (Node orchestrator), `customers/`, `catalog/`, `orders/` (Spring Boot) | the workload; keep the layout `pso create` produced |
| `pso.workspace.json`, `deploy/` | the workspace and the declarative deployments (`shop-*.deployment.pso.ts`, `production.pipeline.pso.ts`), addressed by name; they use the connection name `server` |
| `scenarios/` | the executable validation scenarios (below) |
| `dev-token.mjs`, `dev-jwks.mjs`, `keys/` | the development identity provider used to mint test tokens; `keys/` holds a locally generated signing key and is never committed |
| `artifacts/`, `signed/`, `.tls/` | generated release trees, signed manifests and a private CA: local only, never committed |

## What runs anywhere

Without a server: `pso validate`, `pso pipeline:validate` and `pso release:plan <declaration>` check the workload and the deployment
declarations statically (nothing changes anywhere).

## Scenarios against your own server

The scenarios act on **a real Linux server you own**, reached over SSH. Configuration comes from the environment; nothing is hard-coded
and no secret is stored:

| Variable | Meaning |
|---|---|
| `ECV_HOST` | the server's address |
| `ECV_SSH_USER`, `ECV_SSH_KEY` | the SSH user and the path of your private key (it never leaves your machine) |
| `ECV_HOST_KEY_FP`, `ECV_AGENT_FP` | the server's SSH host-key fingerprint and the PSO agent identity, obtained out of band (`rbac.mjs`) |
| `ECV_TARGET` | `public` (the server's HTTPS port 443) or `tunnel` (default: `127.0.0.1:18443`, for an SSH tunnel you open to that port) |

| Script | Scenario |
|---|---|
| `workflow.mjs` | the Commerce workflow end to end through the gateway, including the asynchronous order decision and a WebSocket channel |
| `ecv.mjs` | the strict-TLS client the scenarios share: trusts only the fixture's private CA, verifies the chain and the address |
| `sec.mjs` | token attacks (none, garbage, tampered signature or claims, `alg=none`, HS256 confusion, expired, wrong audience or issuer, missing scope) |
| `avail.mjs` | availability and latency under light traffic while a PSO command runs |
| `concurrency.mjs` | 12 orders against a stock of 8 while the catalog is redeployed blue-green |
| `recovery1.mjs`, `recovery2.mjs` | local PSO killed mid-deployment; service process killed; deployment worker killed (stale lock, recover); nginx validation failure |
| `rbac.mjs` | restricted identities enrolled with single-use tokens, with real roles |
| `pids.mjs`, `provision-data.mjs`, `bus.mjs` | process-id checks, the database and broker administrator step, the dispatch bus secret |

Add and enroll the connection first (`pso connection:add server ...`, `pso agent:install`, `pso agent:enroll`). The client trusts only the
fixture's private CA and verifies the certificate; there is no TLS bypass.

```bash
cd fixtures/pso-cloud-validation
pso validate
pso release:plan shop-gateway             # plan only: nothing changes on the server
export ECV_HOST=<server address> ECV_SSH_USER=<user> ECV_SSH_KEY=<path to your private key>
node scenarios/sec.mjs
```

A deployment (`pso release:deploy <declaration> --approve`) changes the real server. The `artifacts/` paths named in `deploy/` must be
built first (build each service, then package the gateway with `packages/deploy/test/fixtures/real-pso/package-gateway.mjs`).
